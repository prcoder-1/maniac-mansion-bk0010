# Известные баги кросс-тулчейна `pdp11-aout-gcc` (-Os)

Патченный кросс-`gcc` для БК-0010 (`pdp11-aout`, флаги `-m10 -m1801vm1 -Os`)
даёт **неверный код** в двух известных случаях. Оба проявляются как «логика
на Си правильная, а на БК ветка выполняется не та»; отлаживаются только
дизассемблированием (`pdp11-aout-objdump -d file.o`).

## 1. Материализация bool из uint8_t-сравнения (clr стирает флаги)

**Симптом:** условие, переданное значением — `f((st & bit) != 0)`,
`cond = (m == 0)` — над `uint8_t`-операндами **всегда равно 0**. В движке
из-за этого все условные опкоды состояний (`ifState01..08`,
`ifNotState01..08`) уходили в ветку «условие ложно»: Open запертой двери
шёл в locked-ветку даже после `clearState04` (исправлено в `25d36f1`).

**Причина:** gcc генерирует вычисление условия через флаги
(`neg`/`dec`/`xor` ставят N/C), а затем шаблон материализации:

```
neg r0        ; флаги выставлены по результату
clr r0        ; !!! CLR на PDP-11 сбрасывает И флаги (N=0,Z=1,V=0,C=0)
tst r0        ; тестирует уже обнулённый регистр
bge .+2       ; ветвление видит «ноль», а не исходный результат
inc r0
```

`CLR` между операцией и ветвлением уничтожает condition codes — результат
всегда 0. Переписывание на явные ветки (`if (m) cond = 1;`) **не помогает**:
if-conversion сворачивает их обратно в тот же битый шаблон.

**Лечение:** не давать компилятору материализовать bool — ветвиться сразу
по значению, без промежуточной переменной-условия и без передачи сравнения
аргументом:

```c
/* БЫЛО (всегда прыгает): */
jumpRel((st & bit) != 0);

/* СТАЛО (безопасно: tstb/bne прямо перед действием): */
uint8_t m = (uint8_t)(st & bit);
int16_t o = fwords();
if (sop == 3) { if (!m) sp += o; }   /* if:    бит снят -> прыжок */
else          { if (m)  sp += o; }   /* ifNot: бит есть -> прыжок */
```

**Как распознать в objdump:** последовательность `clr rN; tst rN; bge`
сразу после флаго-ставящей операции (`neg`/`dec`/`xor`/`bicb`). Замечание:
`jumpRel(a == b)` с `int16_t`-операндами (сравнения `isEqual` и т.п.)
эмпирически работает — но при странном поведении сравнений проверять
первым делом это место.

## 2. Цикл по массиву структур с шагом не-степень-2 (`__mulhi3`)

**Симптом:** `for (i = 0; i < N; i++) if (arr[i].field) ...` по массиву
структур, чей `sizeof` — не степень двойки (наблюдалось на слоте 1308 байт),
возвращает неверный результат: `sched_active()` давал 0 при
`arr[0].field == 1` (чтение тем же кодом с константным индексом — верное).

**Причина:** индексация с переменным `i` эмитит умножение на страйд через
`__mulhi3`, и эта комбинация под `-Os` ломается.

**Лечение (любое из):**
- паддить структуры до размера-степени-двойки;
- обходить массив явным указателем: `p = arr; for (...) { ...; p++; }`;
- для маленьких фиксированных N — развернуть с константными индексами
  (`arr[0].f + arr[1].f + arr[2].f`).

## Общее правило

Если на БК «не та ветка» или «не то значение», а Си-код очевидно верен —
сначала `pdp11-aout-objdump -d` подозрительной функции, потом уже логика.
Оба бага — тихие: компилятор не предупреждает, код выглядит осмысленно.

## pdp11-aout-as: дальний BR/Bxx/SOB собирается без ошибки

Если до метки больше 128 слов (у SOB — больше 63 назад), `pdp11-aout-as` не
сообщает об ошибке, а молча обрезает смещение: переход уходит на ±256 слов в
сторону. Так `br back` в `far_fill` (smk.s) прыгал на 01000 байт дальше нужного,
страница вызывающего не возвращалась, и процессор исполнял нули чужой страницы
(HALT -> вектор 4). Псевдокоманд `jbr`/`jeq` с удлинением у этого ассемблера нет.

Защита: правило `%.o: %.s` в Makefile пишет листинг (`-a=`) и проверяет все
переходы скриптом `tools/chkbr.py` (метки именованные и локальные `Nb`/`Nf`).
Дальний переход — `jmp`, условный — обратным условием через `jmp`.

## Без `-mlra`: счётчик переменного сдвига теряется (reload)

Сдвиг на переменную величину gcc раскрывает в цикл `asl rX / dec rN / bne`,
расходующий регистр-счётчик. При высоком давлении на регистры старый проход
reload сохранял счётчик на стек, но второй сдвиг на ту же величину брал уже
обнулённый регистр: в `charset_printChar` (`3 << sh` и `v << sh`) точки знака
оказывались в разряде 0 — вместо букв на экране вертикальные полосы. С `-mlra`
(новый распределитель) счётчик копируется перед циклом. Ключ стоит в CFLAGS.

## libgcc: `__divsi3` (и всё 32-битное деление) считает неверно

**Симптом:** при ходьбе влево актёр шёл спиной или боком, на хосте — правильно.
В `calcMovementFactor` (actor.c) `(-65536 * -20) / -12` дало **-8191** вместо
-109226: умножение верно (`1310720`), неверно деление `__divsi3` из `libgcc.a`
(pdp11-aout, gcc 14.2, msoft-float). Угол `getAngleFromPos` выходил 0 вместо 270.
Хост этого не видит: там деление делает процессор ПК.

**Проверка:** отдельная программа на эмуляторе, 200 пар (знаки, края, случайные
32-битные), сверка с Python: `__mulsi3` из libgcc — без ошибок; деление — нет.

**Решение:** свои `___udivsi3`, `___umodsi3`, `___divsi3`, `___modsi3` на
ассемблере (`mathsi.s`, общая копия кода: символы видны ядру и банкам, член libgcc
не подтягивается). Те же 200 пар — без ошибок. Затронуты были также
`closestPtOnLine` (room.c) и `getRandomNumber` (platform.c, `% (max + 1)`).

**Правило:** из libgcc в сборке остаётся только `mulsi3.o` — проверять
`grep libgcc.a( *.map` после изменений.

## Сравнение int32: младшие слова — со знаком

**Симптом:** метеорит в демо поднимался к луне вместо падения, дети при ходьбе
уходили вверх; на хосте — правильно. `deltaYFactor` = 60395 (0x0000EBEB), а шаг
`a->y += deltaYFactor > 0 ? 1 : -1` шёл вверх.

**Причина:** gcc 14.2 (pdp11) раскладывает сравнение int32 на два сравнения слов, но
после равенства старших слов берёт **знаковый** переход по младшим. Для
`if (d != 0) … d > 0` код такой: `tst hi; bne L; tst lo; L: beq …; ble …` — при
нулевом старшем слове знак берётся из младшего, и 0x0000EBEB «меньше нуля». Так же
`l <= r` в `compareSlope`, `d < best` в `getClosestPtOnBox`, `delay < 0` в
`decreaseScriptDelay`, знаки в `getAngleFromPos` / `remapDirection`.

**Решение:** `cmp32(a, b)` (-1, 0, 1) на ассемблере (`mathsi.s`: старшие слова —
со знаком, младшие — без) и `sgn32(a)`; все `<`, `>`, `<=`, `>=` и проверки знака
для int32 — только через них (scumm.h). Беззнаковые uint32 сравниваются верно.

**Ещё:** `(uint16_t)(x >> 16)` от поля int32 в структуре читает младшее слово, а не
старшее (видно в отладочном дампе). В игровом коде таких мест нет.

**Сборка gcc от 2026-10-07** (cc1 и libgcc пересобраны) сравнивает int32 верно:
`cmp hi; blt/bne; cmp lo; blos`. `cmp32` оставлен — защита для старых сборок.

## far_rd пишет только в базовое ОЗУ

Не ошибка компилятора, но ловушка того же рода (на хосте не видна): `far_rd(dst,
page, …)` подключает страницу-источник и копирует в `dst` — если `dst` в окне
0100000..0157777 (статический массив банка), данные уходят в ту же страницу.
Так боксы комнаты (`boxes`, банк B) не загружались вовсе, а копия комнаты в кэше
портилась: актёры ходили мимо боксов. В банк — только `far_cp(PG_BANKx, …)`.

### r5 не сохраняется, если функции понадобился указатель кадра (gcc 14.2, `-fomit-frame-pointer`)

Обычно gcc pdp11 сохраняет r5 в прологе (`mov r5, -(sp)`), как r2–r4. Но если
функции нужен указатель кадра — например, есть локальная структура, адрес
которой уходит в вызов, или много аргументов на стеке при `-fomit-frame-pointer`, —
она пишет `mov sp, r5` и сохраняет только r2–r4:

    _walkActorToActor:
        mov r2, -(sp); mov r3, -(sp); mov r4, -(sp)
        mov sp, r5            ; r5 вызывающего потерян

Вызывающий, который сам держит в r5 указатель кадра (`executeOpcode`: эпилог
`mov r5, sp`), после возврата снимает со стека мусор и уходит по мусорному
адресу — trap 4. Так падала игра, когда на звонок выходил Эд
(`o5_walkActorToActor`).

Обход: таким функциям — `FP_SAFE` (scumm.h, `__attribute__((optimize("no-omit-frame-pointer")))`):
тогда пролог сохраняет r5. Глобальный `-fno-omit-frame-pointer` тоже лечит, но
код растёт на ~14%. Сборка проверяет каждый объектник из Си
(`tools/chkr5.py`, правило `%.o: %.c` в Makefile) и останавливается, если
функция пишет r5, не сохранив его.
